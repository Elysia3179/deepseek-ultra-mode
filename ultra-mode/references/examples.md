# 示例：触发边界与前后对比

## 一、触发 / 不触发判定表

| 用户输入 | 是否启用 | 理由 |
|---|---|---|
| 「ultra mode：帮我把这个模块重构了」 | ✅ 启用 | 显式口令 |
| 「这个方案我要拿去给老板汇报，帮我压一遍」 | ✅ 启用 | 结果对外使用，错误代价高 |
| 「线上支付回调偶发重复扣款，查一下」 | ✅ 启用 | 排障 + 不可逆 + 难以自证 |
| 「这个 SQL 迁移脚本能直接在生产跑吗」 | ✅ 启用 | 不可逆 |
| 「帮我查下 Python 里 dict 的 get 默认值」 | ❌ 不启用 | 一句话事实查询 |
| 「给我一句话结论就行」 | ❌ 不启用 | 用户显式要求简短（优先级高于本技能） |
| 「帮我想 20 个公众号标题」 | ❌ 不启用 | 创意发散，无对错标准 |
| 「循环处理这 5000 条数据，怎么调 API 最省」 | ❌ 不启用 | 成本是被优化的目标本身 |
| 「这个报错什么意思」 | ❌ 不启用 | 若报错信息完整，属一句话查询；若需排障，用户会追问 |

### 三个容易误触发的场景

1. **用户说"详细一点"** —— 这是要**长度**，不一定要**深度**。先给结构化详版；若发现用户其实需要的是"更多验证"，再升级为 Ultra Mode。
2. **用户说"认真做"** —— 情绪表达，不构成技术约束。默认按普通模式，但把自检清单跑一遍即可。
3. **上下文已 80% 满** —— 即使命中触发条件，也应先说明预算限制并建议拆任务（R9 优先于穷举）。

## 二、同一任务的前后对比

**任务**：「把本地一个技能目录推到 GitHub 公开仓库」

### 普通模式输出（反面）

```text
好的，步骤如下：
1. git init
2. git add .
3. git commit -m "init"
4. 在 GitHub 上新建仓库
5. git remote add origin <url>
6. git push -u origin main

注意替换成你自己的仓库地址。
```

问题：读者照做会在第 3 步报「Author identity unknown」，在第 6 步报认证失败，在第 5 步因为分支名 `master` / `main` 不一致而困惑。每个坑都要自己撞一次。

### Ultra Mode 输出（正面，节选）

```text
结论：可以完成，但有 3 个必踩的坑需要先处理（身份未配置、认证方式未选、分支名不一致）。
下面按"每步给目的 + 命令 + 预期输出 + 失败怎么办"给完整流程。

【第 0 步·环境核查】目的：确认三件事，避免中途卡死
  $ git --version && gh --version
  预期：各自打印版本号
  失败：gh 未安装 → 走"纯网页 + HTTPS 令牌"路线（第 6 步 B 方案），不影响后续

【第 1 步·配置身份】目的：没有它 commit 会直接失败
  $ git config --global user.name "你的名字"
  $ git config --global user.email "你的邮箱"
  预期：无输出（成功即静默）
  验证：$ git config --global user.name → 回显你的名字

【第 3 步·首次提交】目的：建立第一个 commit
  $ git add -A && git commit -m "feat: init ultra-mode skill"
  预期：输出 "1 file changed" 之类的统计行
  失败：出现 "Author identity unknown" → 回第 1 步
       出现 "nothing to commit" → 检查是否漏了 .gitignore 把文件全忽略了

（……后续步骤同格式，略）

【已知缺口】未在你的机器上实跑 push，因为本会话环境访问 github.com:443 被代理拦截
（实测：git ls-remote 返回 "CONNECT tunnel failed, response 502"）。
因此第 7 步的预期输出来自既有认知（C 级），若你的网络需代理，请先执行：
  $ git config --global http.proxy http://127.0.0.1:端口
```

差异：多花了约 3 倍 token，少了一次失败的 push、一次身份报错、一次分支名困惑。

## 三、红队自查记录样例

Ultra Mode 要求阶段 3 主动攻击自己的结论。真实样例：

```text
【红队】我的结论：这个仓库应该命名为 ultra-mode。

反例 1：用户可能想放多个技能，单数命名会限制扩展。
  → 应对：仓库名用 ultra-mode，目录结构预留 skills/ 层，未来可迁移。
  → 判定：暂不改，因为当前只有一个技能，过早抽象是负担。记录取舍。

反例 2：GitHub 上已存在同名仓库，用户创建时会 404 或撞名。
  → 应对：在第 4 步加一句"若提示名称已被占用，改用 ultra-mode-skill"。
  → 判定：采纳，已写入指引。

反例 3：Windows 下目录名 ultra-mode 与文件 SKILL.md 的大小写敏感性。
  → 应对：Git 在 Windows 上默认 core.ignorecase=true，改名可能被忽略。
  → 判定：本任务不涉及改名，记录为已知风险。
```

要求：至少写出一条被证据**推翻或修正**的判断。全绿的红队记录等于没做红队。
